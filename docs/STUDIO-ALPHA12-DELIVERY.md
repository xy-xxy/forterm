# Forterm Studio 0.4.0-alpha.12 交付说明（2026-11-27）

本版修复用户 11-27 在真实堡垒机上报的两个问题：“创建文件夹失败”（截图）和“ssh 的时候点击读取监控后终端就掉线”（附连接诊断）；另外为“堡垒机账户”准备了一个本机脱敏工具。计划和决定见 `docs/STUDIO-REBUILD-PLAN.md`，上一版见 `docs/STUDIO-ALPHA11-DELIVERY.md`。

Core、vendor 的 SSH 库和测试服务器有改动，`Forterm.Desktop` 的行为除下面第 1 项的修复外不变。

## 内容

### 1. 新建文件夹失败（alpha.1 起就有）

- **原因**：SSH 库发送“新建目录”请求时，声明“后面带权限”，却没有把权限值发出去（源码里一行代码被误写进了注释，少了 4 个字节）。OpenSSH 的 `sftp-server` 把它当作不完整的消息，直接退出、不回应；本程序等不到回执，按设计停用了这个文件通道（不知道目录是否建成，不能当作成功）。用 macOS 自带的 `/usr/libexec/sftp-server` 复现过：原来的请求得到“process_mkdir: parse: incomplete message”，补上权限值后目录以 0700 建成并回应成功。
- **影响**：所有经 OpenSSH（以及同样严格的服务器）的 SFTP“新建文件夹”和“上传文件夹”（会先建目录）。`Forterm.Desktop` alpha.36 用的是同一份 SSH 库，也有这个问题（它已冻结，包已按 11-27 的决定删除）。
- **为什么测试没发现**：本地测试服务器会在没收到权限时自己补上 0700。现在它和 OpenSSH 一样严格：消息比它声明的短就关闭文件通道、不回应；只有真的发了权限才使用。另外新增一个测试模式，让 OpenSSH 自己的 `sftp-server` 提供 SFTP（只在临时目录里操作；没有安装它的系统上跳过）。
- 修复后，在旧代码上这些测试都会失败（已实测），在新代码上都通过。

### 2. 文件通道停止后，不再一直“加载中…”

- 一个文件操作没有得到服务器回执、通道被停用之后，文件栏底部说明：“文件通道已停止，文件列表不再更新。如果是刚才的文件操作没有得到服务器的确认，请核对它的结果；还要操作文件时，请从控制器重新打开会话。”
- 之后展开目录会立即显示“读取失败：文件通道已停止”，不再永远显示“加载中…”；操作完成后的自动刷新不再执行，列表保持原样，不会被“刷新失败”盖掉说明。
- 列目录没有在时限内得到回应（不是因为关闭会话）时，显示“读取没有完成：服务器没有回应，或文件通道已停止；收起再展开可以重试”。

### 3. 读取监控后堡垒机断开整个连接

- **诊断显示的情况**：服务器标识 `APACHE-SSHD-2.10.0`。点“读取监控”后，本程序在同一连接上另开一个命令通道执行只读命令（读取 `/proc`、`df`、`ps`）；堡垒机先回应“成功”，约 0.1 秒后没有说明原因就关闭了整个连接，终端也随之断开。这是堡垒机的命令审计或策略，本程序无法改变。另外，这台堡垒机在终端连接上不提供文件通道（打开后立刻结束），文件操作仍要用 xftp 唤醒的会话。
- **现在的做法**（读取监控、结束进程、服务器端压缩、sudo 修改权限都是命令通道）：
  - 控制器唤醒的会话里，第一次打开命令通道前先说明：“有些堡垒机不允许这样执行命令，或按命令审计规则拦截，会直接断开整个连接（终端也会断开）……”，确认后才执行，本会话中不再询问；取消则什么都不发送。
  - 如果连接在打开命令通道后 3 秒内断开，记住这台服务器（数据目录里的 `command-channel-ends.json`，只存地址和端口的哈希，不存地址）。以后连接它时，监控不自动读取；手动读取前会说明“这台服务器上次就在执行命令后不久断开了连接”再问，已保存的连接也一样。
  - 已保存的普通服务器照旧，不询问。
- **连接诊断**：连接在本程序执行命令后 3 秒内结束时，“结果”一行写成“本程序在这个连接上执行命令（读取监控、压缩、sudo 等）0.2 秒后，服务器没有说明原因就关闭了连接”，状态栏也一样。

### 4. 为“堡垒机账户”准备：HAR 脱敏工具

- 用户希望不进浏览器就能登录堡垒机。iframe 页面做不到记录（浏览器不允许读取别的网站在 iframe 里的请求，大多数门户也禁止被嵌入），改为：在浏览器开发者工具里录下登录、连接 SSH 和 SFTP 的过程，导出 HAR。
- `avalonia/tooling/har-summary.py`：只在本机读这个文件、写一份摘要，不联网。摘要保留请求顺序、方法、路径、参数和字段名、状态码、Cookie 名、返回 JSON 的结构和启动地址的形式；密码、动态口令、Cookie 值、令牌、票据、地址、用户名和资产名都替换为“文本(长度)”之类的类型说明。用一份放了假密码、假地址、假票据的记录检查过，输出里一个都没有。
- 堡垒机账户的功能本身要等这份录制，本版还没有做。

## 改动范围

- vendor SSH 库：`Sftp/Requests/SftpMkDirRequest.cs` 补上权限值；补丁记录 `vendor/patches/sshnet-shared-transport.patch` 的这一段按原记录还原出上游后重新生成，并核对过重新应用后与现在的文件一致。
- Core（只增不改）：`KnownHosts.StoreDirectory`；`SshTrace` 记录本程序的 exec 请求时间，用于说明。`Forterm.Desktop` 没有诊断记录，不受影响；构建 0 警告 0 错误。
- Studio：`Services/CommandChannels.cs`（新）；监控、进程管理、压缩、sudo 修改权限在打开命令通道前询问；文件树和文件栏对已停止的文件通道的说明。
- 测试服务器 `tooling/ssh_fixture.py`：严格的“新建目录”，`FIXTURE_REAL_SFTP`、`FIXTURE_MKDIR_HANGUP`、`FIXTURE_EXEC_HANGUP`。
- 版本 0.4.0-alpha.12；数据目录不变。

## 未验证 / 限制

- **新建文件夹的修复没有在你的堡垒机上验证过**：只对 OpenSSH 的 `sftp-server` 和本地测试服务器验证过。你的堡垒机 SFTP 用的是 Apache SSHD，按协议它也应该能处理补上权限值的请求，请实际试一次。
- **读取监控仍可能断开连接**：确认执行后，堡垒机照样会断开，本程序只能事先说明、事后记住。这台堡垒机上建议不要读取监控。
- 记住的“会断开的服务器”只在这台电脑上；目前没有办法在界面上忘掉它（删除数据目录里的 `command-channel-ends.json` 即可）。
- 以下都没有运行过：Windows 10/11 桌面实机、真实凭据库、真实的屏幕阅读器（同 alpha.11）。
- 安装包没有数字签名。

# Forterm Studio 0.4.0-alpha.16 交付说明（2026-11-28）

用户在真实堡垒机上用 alpha.15 后报的三件事：堡垒机的 SFTP 连不上（附连接诊断；用户判断是目标主机的密码不对）；传输管理弹出框向左下展开、超出程序窗口；上传文件到 100%、校验完后提示失败 “failure”。计划和决定见 `docs/STUDIO-REBUILD-PLAN.md`，上一版见 `docs/STUDIO-ALPHA15-DELIVERY.md`。

Core 和 vendor 的 SSH 库有改动，都是只增不改；新行为由两个开关控制，只有 Studio 打开，`Forterm.Desktop` 的行为不变。

## 内容

### 1. 堡垒机结束文件通道时立即说明，带上它的原话

- **诊断显示的情况**：登录成功，打开文件通道后，堡垒机过了 6 秒接受了 SFTP，随后发来一段数据、退出码和“数据结束”，但没有关闭通道。本程序没有把这当成失败，一直等到 30 秒超时，最后只说“文件通道不可用”。用户判断是目标主机的密码不对；堡垒机连不上目标时就是这样结束的。
- **现在**：SFTP 在等待回应时，服务器一旦发来“数据结束”就立即失败；发来退出码时等 0.4 秒再失败，因为服务器常常先发退出码、后发它要说的话。不再等到超时。文件栏说明：
  - “服务器结束了文件通道（SFTP）（退出码 N），没有回应；可能是它没能登录目标主机（例如账号或密码不对），或不允许这样访问”；
  - 堡垒机写在错误输出里的话，或在 SFTP 握手前发来的文字（各最多 2 KiB），清理控制字符后接在后面显示（“服务器说：…”）。这段原话只显示在界面上，不进连接诊断。
- 密码不对本身要在“目标凭据”里改正，或在下拉里选“$user（每次输入）”重新输入。

### 2. 传输管理从按钮向右下弹出

- 原来对齐的是按钮的右边缘、向左下展开；这个按钮靠近窗口左边，弹出框就跑到了程序窗口外面（Windows 上弹出框只受屏幕边界限制）。现在对齐按钮的左边缘，向右下展开。

### 3. 上传 100% 后提示 “failure”

- **原因**：上传的内容校验通过后、提交（改名）前，本程序会按“打开的文件”读取临时文件的属性（SFTP 的 FSTAT），确认路径上的文件就是刚写入的那个。这台堡垒机的 SFTP 不支持 FSTAT，直接回答 “failure”，上传就以这个词失败了。
- **现在**（只在 Studio）：服务器不能按打开的文件读取属性时，改为按路径核对。临时文件建好时、读回内容做校验之前、提交之前各读一次路径的属性：所有者、组和权限要和刚建好时一样，校验之后不能再有变化，仍是普通文件、大小相同，才提交。上传、“新建文件”、编辑器打开、保存和“另存为”都这样做。
- **覆盖已有文件**（包括编辑器保存已有文件）：原文件的所有者和组按路径核对，必须一致；权限先按打开的文件设置，服务器不支持就按路径设置，再按路径读回核对。只有服务器连按路径设置权限也不支持时，才拒绝覆盖并说明原因，旧文件保持不动。

### 4. 打包前独立审查发现并修复

- 一开始只有上传和编辑器读取改用了路径核对；新建文件、编辑器保存和另存为走的是别的路径，在这台堡垒机上仍会报 “failure”。现在这个选项跟着文件来源走，所有文件操作都生效。我自己测试时还发现，按最初的设计，编辑器保存已有文件会被当作“覆盖”而拒绝，那样编辑器在这台堡垒机上就存不了文件；已改为按路径完成覆盖（见上）。
- 服务器先发退出码、后发错误说明时（OpenSSH 常见这个顺序），原来会在说明到达之前就结束，原话丢失；现在退出码之后等 0.4 秒。
- 通道“结束”后紧跟着“关闭”时，可能显示英文的 “Channel was closed.”；现在说“结束”，单独的“关闭”也有中文说明。
- SSH 库的这项改动原来对旧一代 `Forterm.Desktop` 也生效；现在由开关控制，只有 Studio 打开。
- 改用路径核对后，丢了“所有者和权限没被换掉”这一项；现在临时文件建好时就记下所有者、组和权限，校验和提交时都要一致。
- 会话对象重新连接时会带着旧的错误说明和状态；现在每次连接都清空。
- 录制脱敏工具上一版放出的“门户产品编号”字段收窄了：去掉了泛称的 `clientId`，值里不再允许点和横线，地址和主机名不可能漏出。

## 改动范围

- vendor SSH.NET：`SubsystemSession.cs`（子系统结束时立即失败、`SshSubsystemEndedException`、保留错误输出和退出码）、`Sftp/SftpSession.cs`（握手前不像 SFTP 的数据先保留，不当成报文解析）。补丁记录 `vendor/patches/sshnet-shared-transport.patch` 的两段按 CLAUDE.md 的办法生成：`SftpSession.cs` 由原有一段反向应用得到上游版本，`SubsystemSession.cs` 新增一段；重新应用后与现在的文件逐字节相同。
- vendor SSH.NET 还有 `ConnectionInfo.cs`（开关 `SubsystemEndsWaits`）；三段补丁记录都已重新生成并核对。
- Core（只增不改）：`SessionConnectOptions.SubsystemEndsWaits`、`PathStampWhenHandleFails`（默认关闭），`SftpLease.PathStampWhenHandleFails`；`SafeTransfers.Is` 和覆盖时按路径的处理；`SshErrors.Explain` 识别新的异常和“通道已关闭”，`SshErrors.Said`（服务器原话，清理后）。
- Studio：两个开关在终端会话和已保存连接上打开；文件栏显示服务器原话；传输管理弹出方向。
- `tooling/har-summary.py`：门户产品编号的白名单收窄。
- 测试服务器 `ssh_fixture.py`：`FIXTURE_SFTP_ENDS`（及 `FIXTURE_SFTP_ENDS_WITH`：只 EOF、只退出码、先退出码、结束后关闭、退出码后直接关闭）、`FIXTURE_NO_FSTAT`。
- 版本 0.4.0-alpha.16；数据目录不变。

## 验证

- **本机（macOS，Debug）**：Studio 测试 547 项全部通过（比 alpha.15 多 9 项：`Alpha16Tests`——传输管理弹出方向 1 项、不支持 FSTAT 的服务器上的文件操作 1 项、服务器结束文件通道的 6 种方式 6 项、不打开开关时行为不变 1 项）。旧测试（`Forterm.Tests`，含用 OpenSSH 自己的 `sftp-server` 的测试）249 项全部通过；`Forterm.Desktop` 构建 0 警告 0 错误。
- **弹出方向的测试**：第一次写的测试在旧的弹出方向下也通过了。原因是无界面环境里“屏幕”就是窗口，弹出框会被自动翻回窗口内；所以测试改为同时断言弹出方向本身。
- **变异测试**：把本版的修复逐一改回去，13 处中 11 处被测试发现。
  - 有 2 处一开始没被发现（只认 EOF、只认退出码）：测试服务器两样都发，任何一样都能触发。加了只发其中一种的测试后，被发现。
  - 有 2 处始终没被发现：“通道结束后紧跟关闭时，说结束而不说关闭”，同步和异步各一处。SSH 库收到关闭时会先当作收到了 EOF，测试里碰不到这个竞争；按代码审查保留。
- **原生 Mac 窗口（打包产物）**：`native-check.py --idle`、`--looks`、`--clear` 各 12 项全部通过。
- **Mac 入口**：`--runtime-check` 退出码 0（版本 0.4.0-alpha.16）；`xshell --diagnose` 0；`xftp --diagnose … -bogus` 2；`forterm-diagnose` 0 且 `networkRequested:false`；输出里没有密码。
- **Windows CI**（运行 46106025670，提交 73a5566，第一次就全部通过）：Studio 测试 542 项通过、5 项跳过（和以前一样，是 Windows 上不适用的）；入口链路；隐藏启动的入口说明框可见、退出码 2；安装、升级、卸载 51 项检查通过；真实窗口、加背景图片、透明窗口各 23 项全部通过（含用真实鼠标打开三个菜单、关联文件会话）。
- **打包产物**：ZIP 的 290 个文件与发布目录（247 个）加许可证（43 个）逐字节一致；安装包 290 个文件；保留的 Electron 0.1.7 三个包按它的校验文件核对一致。

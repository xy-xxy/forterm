# 原生上传最小现场方案（dev.5，尚未安排执行）

现有事实：用户曾反馈原生选完文件无动作，但已关闭原生，不能复读当时版本及提示。经理看到的Electron0.1.7存在成功项，与原生现场不是同一证据；相邻应用终端日志不属于SFTP上传错误。用户急用可继续已成功的旧版。本方案由经理在用户方便且明确愿意再验证时协调；不自行重开原生或操作生产上传。

## 一次操作同时取得版本和卡点

1. 使用独立新目录的已核验候选；先保存并结束旧原生实例中的工作，再由用户正常启动。不得沿用历史临时票据或重放SSO；用户按正常方式取得新授权会话。原生与Electron是独立应用，不能从当前Electron窗口推断原生版本。普通主窗口标题显示版本，独立会话窗口的标题可能只含名称，以阶段JSON内version为准。
2. 在用户明确允许写入、且已有成功经验的已知目录读取列表；不猜目录、不把失败路径转为写入目标。只选一个用户允许上传的小普通文件，点一次打开。覆盖必须人工确认；不为了诊断选择覆盖生产文件。
3. 只观察一次：队列是否出现、运行/排队/失败数量及具体等待阶段。目标核对/开启流通常由10秒元信息边界约束，已开启数据流以30秒无字节进展为停滞边界；这不限制用户主动等待覆盖确认的时间，也不能保证操作系统本地网络盘调用及时返回。不自动重试。
4. 界面响应时，在该文件面板“更多→复制上传阶段信息”，记录固定阶段JSON。只含构建版本、相对计时、状态与阶段，不含路径、文件名、主机/会话ID、错误原文或凭据；复制由用户明确操作，默认不落盘。若正等待覆盖确认，可先按用户决定跳过，再复制；最后phase仍保留覆盖确认，state区分已跳过。
5. 若整个窗口不响应，无法复制，保留当前画面和“打不开更多菜单”的事实，不把空JSON/缺事件记成0ms或上传成功，也不要重复选择文件。经理再决定是否需要独立进程采样；本轮不追加命令注入或生产操作。

## 阶段解释

| 可见证据 | 能确认的范围 |
| --- | --- |
| picker_open_requested，未见picker_closed | 尚未观察到选择窗口关闭；不是已入队 |
| picker_closed，未见picker_callback | Fyne关窗后、调用上传回调前；框架会在其间同步storage.Reader打开本地文件 |
| picker_callback后selection_cancelled | 取消选择，没有新上传 |
| selected_reader_close，未见selected_path_converted | 关闭本地选择器reader或路径转换尚未完成；不等于已入队 |
| selected_path_converted→enqueue_requested，随后upload_rejected | 已收到本地选择，未入队；根据界面明确拒绝原因判断 |
| queue_accepted，state queued | 队列接受，等待串行worker；核对是否已有活动项 |
| target_stat | 在核对目标元信息，尚未打开写入流 |
| overwrite_confirmation | 等待人工覆盖；跳过/关闭借用视图不会写入 |
| file_channel / local_open / remote_open | 分别等待文件通道、读取本地文件、打开远端流 |
| data / close | 数据流阶段或等待关闭确认；state done才表示此次客户端正常完成 |
| state error / cancelled | 失败或已跳过/取消；phase仅表示最后观察阶段，不表示完成 |

dev.5相关新增修复有可重复合成证据，但未知现场问题仍未结案。不要根据旧0.1.7成功、本机合成成功或打包成功要求用户盲目重装/反复上传。

# 原生0.2.2性能排查（开发中）

用户主诉是Windows11 ZIP、未连接时全屏和小窗口任何操作均慢。以下是macOS arm64的合成负载数据，不能当作Windows主诉已经解决。Windows等待链指向dwm.exe是单时点线索，不能直接认定根因，也不应结束DWM或修改系统安全设置。

## 实际输入及仍有的峰值

`actual-input-burst/result.json`为另一次40秒连续输出、200×60实窗；真实CUA点击响应按钮3次，截图显示ACK1/2/3；在终端区域实际Ctrl-C，合成输入端收到且仅收到1字节0x03。共接收25392736字节，结束标记通过，UI排队P95为15.16ms，最大687.85ms。记录没有隐藏这个峰值，也不能据3次点击声称所有输入均已验收。

为继续处理峰值，随后新增每轮约4ms解析预算，在4KiB块之间检查并让出UI，未消费的字节保留到下一轮；仍有32KiB批次上限和有界读取背压。单个块与绘制本身不能被抢占，故这不是硬实时4ms保证。上表和40秒数据属于此自适应预算前的已测实现，更新后另行验证，不混用为最新结果。

精确字宽回归覆盖13/14/16字号、120字符run、ANSI分段、中文宽格、光标、点击格坐标及实际栅格颜色。未对字宽取整，避免长行累计偏移；宽grapheme保持固定格，不为合并对象破坏终端语义。

## 空主窗口与Windows诊断

Mac上0连接/0终端/0队列空窗口，旧新普通/全屏的UI排队P95均低，未复现用户Windows空窗的普遍迟缓，启动时间还受冷缓存等因素影响，不能据单次启动差异下结论。

冻结离线包为`release/Forterm-UI-Diagnostic-0.2.2-diag1-windows-x64.zip`，源码检查点和SHA见PROGRESS顶部。它对照标准Fyne与Forterm空主窗，使用新临时配置与禁用凭据服务，并阻断连接/本地终端入口；不自动读取现有连接、凭据、终端、剪贴板或文件内容，不联网、不发送报告。

报告分别记录UI队列、实际OnTapped计数、native release→OnTapped、OnTapped→下一Raster回调、真实SwapBuffers调用耗时，以及真实GL renderer/vendor/version、framebuffer/缩放和进程资源。Raster生成或SwapBuffers返回仍不是显示器最终呈现时刻。没有实际点击的样本数为0，不写成点击耗时0。小型GLFW本地修订只在主动启用observer时计时，默认nil仍调用原始SwapBuffers。

Windows EXE已交叉构建，尚待用户授权运行和报告；程序员不同时操作经理独占的远程Windows UI。诊断包不替代修复版、美化、新三包与最终复验。


## 后续历史缓冲修订与最新限制

`adaptive-long`单靠解析预算的40秒结果：P95 5.32ms、最大794.55ms、12868384字节，故预算没有消除峰值，且降低了瞬时吞吐。进一步profile显示历史缓冲满后逐行搬移一万条slice header并分配新行，因此改为保留一万行的循环复用，并对两ASCII相邻格跳过不必要的grapheme重新分段；非ASCII/组合符号仍走原分段。历史顺序/输入行克隆隔离/缩容/扩容/清空/宽格尾部/稳定期0分配及VT Unicode/race通过。

`history-200x60`三秒固定负载仍为82590字节，P95 3.58ms；突发P95 4.69ms、最大9.01ms、1153120字节。`history-long`40秒结果为P95 5.78ms、最大758.56ms、14274656字节。最大峰值仍在，不能声称硬实时或完全不卡；这些数字并不能解释或证明修复Win空主窗问题。记录和CPU profile保留，`history-source-hashes.json`标识本阶段代码；早期表格不是把本次后续修订混成同一二进制。
